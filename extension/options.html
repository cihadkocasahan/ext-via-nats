Connect this browser

This Chrome profile joins a NATS subject and waits for commands from an MCP-capable agent. Nothing is polled, no debug port is opened.

1 · Where does your NATS run?

Start a local broker

npm run nats:local

That starts NATS with WebSocket on 127.0.0.1:8222. Already running one, or have a server on your LAN? Skip this and type its address below.

Get your .creds file

  1. Sign in to Synadia Cloud and create an Account.
  2. Inside that account create a User.
  3. Open “Get Connected” for the user and download the .creds file.
  4. Paste the whole file into the .creds field below. The URL field is prefilled with the public cloud WebSocket address; if your account panel shows a different one, use that.

The quick-start guide shows tls://connect.ngs.global — the native NATS client address, which a browser cannot use. This extension speaks NATS over WebSocket, so the cloud preset fills wss://connect.ngs.global:443. That address answers a real NATS handshake; your .creds still authenticates you. Neither the TCP (4222) nor the monitoring (8222) port speaks WebSocket.

The HTTP Gateway is a different door: REST over HTTPS with an Authorization: Bearer API token. This extension does not use it — a browser cannot hold a long-lived request/reply subscription over REST. Use the .creds WebSocket path above.

2 · Connection

Local: ws://HOST:8222 · Cloud: wss://HOST:PORT. Credentials never go inside the URL.

Every subject this profile uses starts with it. Keep it identical in the MCP server config.

Authentication — pick one

Credentials stay in this profile's local extension storage. They are not sent to Chrome Sync and never travel in a NATS message. This storage is not an OS password vault: anyone with this profile can read it.

Commands are authorised by the subject permissions of the NATS account you connect with. Each profile gets its own identity; an email address is not one. An abort request takes effect at the next step boundary.
